### 「확인하는 법」 칸 (`P3` 에서 신설)

`P3` 코드 리뷰에서 **세 결정이 모두 «작동하지 않는 메커니즘» 위에 서 있었던 것**이 드러났습니다:

| 결정 | 근거로 든 메커니즘 | 실제 |
| --- | --- | --- |
| `DEC-036` | *"그건 `check-deps.mjs` 가 잡습니다"* | 규칙이 **저장소의 어떤 파일도 매치하지 않았다** |
| `DEC-037` | *"키 스코프 ∩ 현재 역할, 매 요청 계산"* | **계산하는 경로가 없었다** |
| `DEC-038` | *"`ip`·`userAgent` 는 `Actor` 에 실려 들어온다"* | **아무도 값을 넣지 않았다** |

개별 결함이 아니라 **한 가지 습관**입니다 — 결정을 쓸 때 「이렇게 하면 된다」를 적고 그것이 도는지는 확인하지 않았습니다. 그래서 서식에 한 칸을 더합니다.

| 규칙 | 내용 |
| --- | --- |
| **무엇을 적는가** | 이 결정이 실제로 작동하는지 **한 번 관측하는 방법**. 페이즈 종료 전에 한 번씩 실행한다 |
| **산문 금지** | **명령어·스크립트 경로·테스트 이름**을 적는다. 산문은 주장으로 읽히지만 명령어는 실행되거나 말거나 둘 중 하나다 |
| **결과가 아니라 방법** | 「MEMBER 는 `archive:run` 을 못 만든다」가 아니라 「`scripts/verify-p3-keys.ts` 를 돌린다」. **관측 결과를 적으면 그 문장이 다음 사람에게 코드보다 먼저 읽힌다** — `P3` 에서 리뷰어가 주석을 코드로 읽고 오탐을 낸 사례가 있었다 |
| **가리키는 파일은 지우지 않는다** | 「임시」로 보이는 이름(`_` 접두사 등)을 쓰지 않는다. 지우면 그 결정이 다시 관측 불가로 돌아간다 |

### DEC-005 — 세션: DB 세션 + Redis 캐시 (JWT 아님)

> **상태: 폐기 (`DEC-030` 으로 대체).**
> **요구(«DB 세션 + 즉시 반영»)는 옳았고 그대로 유지합니다.** 폐기한 것은 **수단**입니다 —
> Auth.js 는 Credentials Provider(`DEC-002`)를 쓰면 세션 전략이 **JWT로 고정**되어
> database 세션을 쓸 수 없습니다. 두 결정이 서로를 무효화하고 있었습니다.

| 항목 | 내용 |
| --- | --- |
| **결정** | Auth.js 의 database 세션 전략을 쓰고, 조회 부하만 Redis로 캐시한다 |
| **검토안** | ① DB 세션 ② JWT 세션 |
| **근거** | 승인·정지·역할 변경을 **즉시 반영**해야 한다. JWT는 발급 후 서버가 취소할 수 없다 |
| **영향** | 요청마다 세션 조회가 필요하다 → Redis 캐시(15분)로 완화. 사용자별 세션 인덱스를 Redis Set으로 관리해 강제 로그아웃을 구현한다 |
| **결정일** | 2026-08-28 |

### DEC-048 — 전문 검색은 **관련도 상위 2,000건 안에서만** 본다. 그리고 그 사실을 화면이 말한다

검색은 raw SQL 로 **id 만** 뽑아 Prisma 의 `where` 에 합칩니다(`id IN (…)`). 조립·정렬·페이징은 그대로 Prisma 가 하므로 `DEC-045` 의 「`P4` 가 만들고 `P8` 이 얹는다」가 검색 경로에서도 성립합니다. 그 대가가 **후보 상한**입니다.

| 항목 | 내용 |
| --- | --- |
| **결정** | 전문 검색은 **관련도 상위 `2000`건 안에서만** 필터·정렬·페이징한다. 상한에 닿으면 **화면이 그 사실을 말한다.** 상한은 이 2단 구조의 **요구사항**이지 임의값이 아니다 |
| **검토안** | ① 후보 방식 유지 + 상한을 결정으로 승격 ② raw 를 본 질의로 올려 상한 제거 ③ 상한만 올림(예: 20,000) |
| **근거 ① 구조가 상한을 요구한다** | `id IN (…)` 리스트가 커지면 Postgres 파싱 비용이 급격히 나빠진다. 상한을 없애려면 ②가 되고, ②는 select·정렬·페이징을 raw 와 Prisma 두 곳으로 가른다 — **`DEC-045`(`P8` 관리자 목록이 같은 함수를 쓴다)와 정렬 허용 표 단일 출처(`list.schema.ts`)가 동시에 깨진다.** ③은 문제를 미룰 뿐 같은 벽을 만난다 |
| **근거 ② 없애는 것보다 «보이게» 하는 것이 지금 규모에서 옳다** | 자료 1만 건·동시 20명에서 흔한 검색어가 2,000건을 넘는 일이 아직 없다. **페이즈 끝에서 목록 파이프라인을 다시 쓰는 것은, 합성 데이터에서만 보이는 문제에 대한 값으로 너무 크다** |
| **남는 한계 (명시)** | **`ts_rank` 는 FTS 분기만 정렬한다.** `title ILIKE` 로만 걸린 행은 전부 `rank = 0` 동점이고, Postgres 는 동점을 임의 순서로 낸다 — 즉 **절단이 관련도 기준이 아니다.** `, id DESC` 는 절단을 «의미 있게»가 아니라 **«안정되게»** 만든다. 또한 raw 에 `status` 를 넣지 않으므로 `DRAFT`·`ARCHIVED` 행이 후보 자리를 차지해 **실효 상한은 2,000보다 낮다** — 넣으면 `toWhere` 의 필터 판정이 SQL 로 복제되므로 넣지 않고, 아래 신호가 그 손실까지 포함해 말한다 |
| **이 결정이 고친 거짓말** | 이 자리 주석은 *"관련도 순으로 자르니 잘리는 것은 항상 «덜 관련된 것»"* 이라고 적혀 있었다. 거짓이다. 게다가 동점 순서는 실행마다 달라질 수 있어 **같은 검색이 요청마다 다른 결과를 낼 수 있었다** — 잘림보다 이쪽이 나쁘다. `DEC-036`·`037`·`038` 에 이어 **코드가 갖지 않은 성질을 주장한 주석의 네 번째 사례**다 |
| **확인하는 법** | `npx tsx --conditions=react-server --env-file=.env scripts/verify-p4.ts` — 「검색 후보 상한」 항목: ① 상한을 넘기면 `searchTruncated` 가 `true` 이고 ② **같은 질의를 두 번 하면 같은 결과**가 나온다. 신호는 `LIMIT 2001` 한 건을 더 뽑아 얻으므로 별도 `COUNT` 가 없다 |
| **재검토 시점** | 실데이터에서 흔한 검색어가 2,000건을 넘기 시작할 때. 그때는 raw 를 본 질의로 올리고 keyset 페이징으로 간다 |
| **영향** | `resource.repository.searchIds` 가 `{ ids, truncated }` 를 돌려준다 · `ListResult`·`ListPage` 에 `searchTruncated` · `ResourceBrowser` 가 안내를 띄운다 · `DEV-05` 검색 API 응답에 같은 필드가 필요하다 (`P7`) |
| **결정일** | 2026-08-28 |

#### `FR-SRCH-006` — 옮긴 것이 아니라 **중복을 정리한 것**이다

이 구분이 흐려지면 다음에 진짜 `P0` 누락이 「중복이었다」로 포장됩니다.

`FR-SRCH-006` 은 「2단계 트리로 카테고리를 **관리**한다」(`P0`)였고 `M2` 작업표에 있어, `P4` 를 닫으려는데 「`P0` 인데 안 만들었다」로 걸렸습니다. 그런데 **`FR-ADM-012`「카테고리 관리 — 생성·수정·순서 변경·삭제(자료 이관 포함)」(`P0`)이 v0.1 부터 있었고**, `M5` 작업표·`SCR-231` 정의·`DEV-03 · 3.14` 화면 대응표 **세 곳**에 이미 잡혀 있었습니다. 그 대응표는 `FR-SRCH-006` 에 화면을 하나도 주지 않습니다 — CRUD 요구사항은 전부 화면이 있는데 이 번호만 없습니다.

| 「2단계 트리로」 | **구조 제약.** 다른 어떤 요구사항도 이 말을 하지 않는다. `trg_categories_depth` 트리거가 DB 에서 강제 중 — **`P4` 가 이미 충족했다** |
| 「관리한다」 | **CRUD.** `FR-ADM-012` 가 이미 소유 |

**「관리」를 떼고 구조 제약만 남깁니다.** 우선순위 `P0` 그대로, 마일스톤 `M2` 그대로, 총 요구사항 105건 그대로 — **폐기가 아니라 문장 축소**입니다.

> **좁히기를 허용하는 조건 (조항으로 남깁니다).**
> 요구사항 문장을 좁히는 것은 **그 일을 이미 맡은 «다른 번호»가 이 대화 이전부터 존재할 때만** 허용된다. **그 번호를 지금 만들어서는 안 된다.** 조건이 안 맞으면 그것은 범위 축소이고, 그때는 못 좁힌다.
>
> `FR-ADM-012` 는 세 문서에 이미 있었고 **계획에서 빠져나간 일이 0** 이므로 조건을 만족합니다.

작업표는 행을 쪼갭니다 — `M2` 는 「카테고리·태그 **사용**(필터·폼 선택·상세 표시)」, `M5` 의 「분류 관리」 행은 손대지 않습니다. **이건 이 문서가 이미 쓰는 서식입니다** — `FR-ADM-014` 가 `M2`(「조회 + 사이드바 병합」)와 `M5`(「노출 설정」)에 같은 번호로 두 번 들어 있고, 무엇을 어디서 하는지는 작업 칸의 문장이 가릅니다.

#### `movedTo` 같은 필드는 두지 않는다

「이 번호는 다른 페이즈로 옮겼다」를 `DEBT` 에 적게 하면 **세 번째 정본**이 생깁니다(FR 문서 우선순위 · 로드맵 작업표 · 코드의 목록). `DEV-07 · 7.11` 이 이미 *"같은 사실을 두 곳에 두고 한쪽을 축약하면서 조항 하나가 사라졌다"*(`P3` 의 API 키 무효화)고 적어 뒀습니다 — 두 곳도 사고를 냈습니다. 그리고 자기 신고 필드는 `DEC-044` 가 말한 **「인자」**입니다.

**「옮긴다」는 조작 하나로 정의합니다: 번호를 한 작업표 행에서 빼고 다른 행에 넣는 것.** 그러면 지금 검사기가 추가 코드 없이 검증합니다 — 앞 마일스톤은 더 이상 안 묻고, 뒤 마일스톤이 닫힐 때 묻습니다.

**남는 구멍은 `DCS-02` 로 옮깁니다** — 「어느 작업표에도 없이 사라지는」 경우는 자기 신고로 못 잡고 **REQ-03 의 모든 `P0` 가 로드맵 어딘가에 나타나는가**라는 집합 차집합으로 잡힙니다. 같은 파서가 `DEBT` 의 `priority` 손으로 적기와 「`P0` 는 부채 금지」가 **아직 주석뿐인 것**도 함께 해결합니다.
