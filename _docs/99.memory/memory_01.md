## [005] 2026-08-28 · MinIO 제외 → 로컬 파일시스템 저장

- **결정** — `DEC-019` (기존 `DEC-003` 폐기)
  - 첨부·아카이브를 **앱 서버의 로컬 파일시스템**에 직접 저장한다. MinIO 컨테이너를 쓰지 않는다.
  - `STORAGE_ROOT` = `E:\queenbee-data\files`. Docker 컨테이너는 `postgres`·`redis` **2개**로 줄었다.
  - `StorageDriver` 인터페이스는 유지한다. 지금은 `local` 구현 하나뿐이고, 필요해지면 `s3` 를 추가한다.

- **이유**
  - 1단계는 개발 PC 단독 운영이다. 컨테이너를 하나 줄이면 세팅·백업·장애 지점이 모두 단순해진다.
  - 파일은 어차피 같은 디스크에 저장된다. presigned URL의 이점(앱 서버 우회)은 동시 20명 규모에서 실익이 작다.
  - **백업이 폴더 복사로 끝난다.** 버킷 동기화 절차가 사라졌다.

- **연쇄로 바뀐 것 (중요)**
  - **presigned 방식이 통째로 사라졌다.** 파일이 앱 서버를 통과한다.
  - 업로드는 **Route Handler 스트리밍**(`API-040`). Server Action은 본문 크기 제한이 있어 못 쓴다.
    `tmp/{uuid}` 에 먼저 쓰고 검증 후 `rename` — 같은 볼륨이라 원자적이다.
  - 다운로드는 **스트림 응답 + `Range` 지원**(`API-042`·`API-032`). 아카이브가 500MB까지라
    끊겼을 때 처음부터 다시 받게 하면 안 된다.
  - `API-041 confirmUploadAction` 폐기 (presigned 전용이었다). 번호는 재사용하지 않는다.
  - **새 보안 요구 3건** — `NFR-SEC-019` 경로 이탈 방어, `NFR-SEC-020` 응답 헤더,
    `NFR-SEC-021` 접근 통제. 키를 파일 경로로 쓰게 되면서 생긴 위험이다.
  - `NFR-PERF-007` 스트리밍 강제 (파일을 메모리에 통째로 올리지 않는다).
  - Windows 주의사항 추가 — 열린 파일 삭제 불가, 경로 구분자는 디스크 접근 직전에만 변환.

### 검토 결론

**M0(인프라)·M2(자료 코어)는 문서를 그대로 따라가면 된다. 그런데 M1(인증)은 만들 수 없었다.**
결정 두 개가 서로를 무효화하고 있었기 때문이다.

### 1. 가장 큰 발견 — `DEC-002` 와 `DEC-005` 가 양립하지 않았다

| 결정 | 내용 |
| --- | --- |
| `DEC-002` | 인증은 **Auth.js v5 Credentials Provider** |
| `DEC-005` | 세션은 **Auth.js database 세션** + Redis 캐시 |

**Auth.js 는 Credentials Provider 를 쓰면 세션 전략이 JWT 로 고정된다.** 어댑터의 `Session`
테이블은 채워지지 않는다. 그런데 이 표에 매달려 있던 설계가 다섯 개였다 —
`TBL-sessions`, Redis `user:sessions:{userId}`(강제 로그아웃용), `API-063/065`(정지 시 세션 전체 삭제),
`FR-USER-006`(활성 세션 목록), `REQ-05` E2E ⑤(정지 → 즉시 로그아웃). 전부 같이 무너진다.

**→ `DEC-030`: Auth.js 를 아예 쓰지 않고 세션을 직접 만든다.**

결정적이었던 근거는 «구현이 어렵다/쉽다»가 아니라 **«우리는 Auth.js 가 주는 것을 안 쓴다»** 였다.
소셜·SSO를 도입하지 않기로 했으므로(`DEC-002`) 프로바이더 생태계·계정 연결·OAuth 흐름이 전부
불필요하다. **남는 것은 제약뿐이었다.** 직접 짜는 범위도 좁다 — 암호는 Argon2id 라이브러리가 하고
우리가 만드는 것은 «랜덤 토큰 발급 · 해시 저장 · 조회 · 폐기» 넷뿐이다.
Next.js 공식 authentication 가이드가 이 형태를 그대로 문서화하고 있다.

- `DEC-005` 는 **폐기가 아니라 «수단만» 폐기**로 적었다. «DB 세션 + 즉시 반영»이라는 **요구는 옳았다.**
- 세션 토큰은 DB에 **SHA-256 해시로만** 둔다 (API 키와 같은 원칙). Redis 키도 해시를 쓴다 —
  원문이 캐시에 남으면 DB에만 해시로 둔 의미가 없다.

### 2. `proxy.ts` 를 «인가 1계층»이라 부른 것 — `DEC-031`

Next.js 16 번들 문서(`node_modules/next/dist/docs`)를 직접 열어 확인했다.

- proxy 는 **Node.js 런타임이 기본**(`v16.0.0` 변경)이라 DB 접근이 불가능하진 않다. 그런데
  공식 문서가 *"full session management or authorization solution 으로 쓰지 말 것"*,
  *"prefetch 포함 모든 라우트에서 실행되므로 DB 조회를 피할 것"* 이라고 명시한다.
- **더 결정적인 것:** Server Action 은 별도 라우트가 아니라 **그 경로로 들어오는 POST** 다.
  `matcher` 가 제외한 경로면 proxy 를 그냥 건너뛴다. 문서가 *"proxy 에만 의존하지 말고 각
  Server Function 안에서 인증·인가를 확인하라"* 고 못 박고 있다.

→ **1층은 낙관적 걸러내기, 실제 인가는 3층.** `DEV-05 · 5.10` 의 «액션 6단계»가 선택이 아니라
**유일한 방어선**이 됐다. 그리고 1층이 DB를 안 보므로 `status`·`role` 이 쿠키에 실려야 하는데,
그 최신성은 `DEC-030` 의 DB 세션이 보장한다 — **두 결정이 맞물린다.**

### 3. 콘텐츠 타입 설정의 이중 출처 — `DEC-032`

`content_type_settings` 에 `label`·`description`·`icon` 컬럼이 있는데 코드 레지스트리에도 같은 값이
있었다. **`DEC-029`(`needs_review` vs `source_channel`)에서 겪은 것과 똑같은 문제** — 한 사실을
두 곳에 두면 어긋났을 때 판단 근거가 없다.

→ **표현은 코드, 운영 설정(`is_active`·`show_in_nav`·`sort_order`)만 DB.** 컬럼 3개 제거.

병합 지점도 없었다. `buildResourceNavGroup()` 이 **클라이언트 컴포넌트**에서 레지스트리 상수만
읽는다(`icon` 이 함수라 서버→클라이언트 경계를 못 넘어서 그렇게 짠 것이고, 그 판단 자체는 옳다).
그대로 두면 M5의 `FR-ADM-014`(관리자 타입 노출 설정)가 동작하지 않는다.
→ **서버가 `{code, isActive, showInNav, sortOrder}` 만 넘기고 클라이언트가 `code` 로 병합**한다고

시드가 파싱되지 않았다. Node 의 타입 스트리퍼와 esbuild **둘 다** 177행에서

```

                                            ^^ 여기서 블록 주석이 끝난다
```

- **블록 주석 안에 `*/` 가 생기는 문자열을 쓰지 말 것.** 경로에 글로브를 쓰지 말고 `<type>` 으로 적는다.

- 저장소 전체를 훑어 같은 패턴이 더 없는지 확인했다 (`*/` 뒤에 문자가 붙는 경우) — 0건.

→ **세대(generation) 카운터.** 무효화는 `INCR user:gen:{userId}` **한 번**이고 캐시 값에

키를 지울 필요가 없어졌기 때문입니다.
캐시 값에 `expiresAtMs`·`idleSinceMs` 도 넣었습니다. 없으면 캐시 히트 경로가
**만료를 한 번도 검사하지 않습니다.**

#### H5 — 오픈 리다이렉트가 열려 있었다

`startsWith("//")` 검사는 **탭·개행을 못 막습니다.** WHATWG URL 파서가 `\t`·`\n`·`\r` 을
**위치와 무관하게 제거**하므로 `/%0A/evil.com` → `//evil.com`(프로토콜 상대 URL)이 됩니다.
→ 문자 비교를 버리고 **파서에 맡겨 정규화된 값**을 돌려줍니다. 7가지 입력으로 확인했습니다.

#### H6 — `x-forwarded-for` 를 무조건 믿었다

주석에는 「신뢰할 상황은 아니지만」이라고 써 놓고 코드는 그대로 썼습니다.
헤더를 매번 바꾸면 **IP 20회/10분 제한이 완전히 무력화**되고 감사 로그 IP 도 오염됩니다.
→ `TRUST_PROXY` 환경 변수(기본 `false`). **「막고 있다고 믿는 코드」보다
「이 단계에서는 IP 제한이 유효하지 않다」고 말하는 코드가 낫습니다.**

#### H4 — 시드의 `NODE_ENV` 판정이 fail-open 이었다

시드는 `next` 와 **다른 프로세스**(`tsx`)라 `NODE_ENV` 가 대개 비어 있습니다.

### 1. 강제 장치가 작동하지 않고 있었다 — `DEC-044`

`DEC-036` 은 「무효화를 빠뜨린다」를 「`status`·`role` 을 다른 데서 쓴다」로 바꾸면
**grep 이 된다**를 근거로 세운 결정이었습니다. 그 grep 이 이랬습니다:

```js
/\b(?:db|tx)\.user\.update(?:Many)?\s*\(\s*\{[\s\S]{0,400}?\b(?:status|role)\s*:/
```

**인자를 봅니다.** 그런데 정당한 작성자(`member.service`)조차 `tx.user.update({ where, data })`
로 `data` 를 변수에 담기 때문에 **저장소의 어떤 파일도 이 규칙에 매치하지 않았습니다.**
일부러 우회 파일 셋을 만들어 던졌더니 전부 통과했습니다:

| 형태 | 옛 규칙 |
| --- | --- |
| `const patch = {status}; db.user.update({data: patch})` | 통과 |
| `` db.$executeRaw`UPDATE users SET status…` `` | 통과 |
| `import { db as client }` 후 `client.user.update` | 통과 |

> **「위반 0건」이 규칙이 아무것도 보지 않아서 나온 0건이었습니다.**
> 게이트가 거짓말하면 게이트가 없는 것보다 나쁩니다 — 그 위에서 내린 판단이 전부 오염됩니다.

**내가 이 규칙을 「실제로 잡는지 확인했다」고 P3 중간에 보고했었습니다.** 시험에 쓴 것이
정규식이 잡는 **유일한 형태**(인라인 객체 리터럴)였습니다. **검증은 「통과하는 것」이 아니라
「빠져나가는 것」으로 해야 합니다.**

고친 방식: **인자를 보지 않고 호출 «위치»만 봅니다.** 인자를 보면 우회 형태가 무한하고
위치를 보면 유한합니다. 허용 목록의 길이가 곧 「그 테이블로 가는 문의 개수」라 리뷰에서 보입니다.
`layerOf()` 가 `../` 를 무조건 통과시켜 **FORBIDDEN 8개 규칙 전체가 우회 가능**했던 것도
같이 고쳤습니다(주석은 *"상대 경로는 `./` 만 허용하므로"* 였는데 **강제하는 것이 없었습니다**).

새 게이트를 켜자마자 위반 2건이 나왔습니다 — 호출자 0인 `member.repository.updateStatus`
(**두 번째 문**)와 `/pending` 의 인가 없는 인라인 액션. 둘 다 아키텍트가 예고한 것이었습니다.

### 2. 주석이 코드의 알리바이 노릇을 하고 있었다 — H1

`session.resolve` 가 정지된 사용자를 최대 15분 되살리는 경합이 있었는데,
그 자리 주석은 *「후자를 막기 위해 **세대를 DB 조회 직전에 읽습니다**」* 라고 **단언**했습니다.
코드는 정반대였고, 애초에 **구조상 불가능**합니다 — 세대 키가 `user:gen:{userId}` 라
`userId` 를 알기 전에는 읽을 수 없고 `userId` 는 그 조회로 알게 됩니다.

막은 방법은 세대를 앞당기는 게 아니라 **`touch()` 가 이미 하던 존재 확인의 결과를 버리지
않는 것**이었습니다. 질의가 하나도 안 늘었습니다. 창을 40ms 로 넓혀 실측:

| | 존재 확인 없음 | 있음 |
| --- | --- | --- |
| 정지 후 세션이 살아남은 라운드 | **40/40** | **0/40** |

> **세대 카운터와 존재 확인이 서로의 창을 덮습니다.** 어느 하나만으로는 열립니다.

### 3. 「전달했다고 믿는 코드」 — `DEC-041`

거부·정지 시 사유가 담긴 알림 행을 정성껏 만들고 있었는데, 그 사람들은 **로그인이 막혀
알림함에 영원히 도달할 수 없습니다.** 로그인 화면 문구는 고정 문자열이었고,
관리자 화면은 *「사유는 본인에게 그대로 전달되고」* 라고 **관리자에게 거짓말**하고 있었습니다.

같이 나온 것: `WITHDRAWN` 문구가 "탈퇴한 계정입니다."였습니다. 실패 메시지를 통일하고
(`REQ-02 · 2.6`) argon2 로 타이밍까지 평준화해 놓고 **탈퇴 계정만 「이 아이디는 있었다」를
알려 주고 있었습니다.** 규격(`FR-AUTH-007`)은 "존재하지 않는 계정입니다"였습니다.

### 4. 내가 방금 고친 문제를 그 자리에서 다시 만들었다

거부 사유 길이가 서버·클라이언트에 각각 하드코딩된 것을 `features/members/schema.ts`
한 곳으로 합쳐 놓고, **바로 다음 항목에서 `RESETTABLE` 배열을 서비스와 화면에 두 벌** 썼습니다.
타입 오류로 알았습니다. 원칙을 아는 것과 지키는 것은 다릅니다 —
그래서 검사기가 있는 것이고, **「같은 상수 두 벌」은 아직 어떤 검사기도 못 잡습니다.**

### 5. 검증 방식

`[018]` C1 의 교훈(«service 검증은 화면 검증이 아니다»)대로 **dev 서버에 세션 쿠키를 들고
HTTP 로 요청해** 응답과 렌더된 HTML 을 봤습니다. **28항목 전부 통과.**

한 항목이 실패했는데 **코드가 아니라 내 단정이 틀렸습니다** — React 는 텍스트와 표현식
사이에 `<!-- -->` 를 넣어서 `승인 대기 {n}건` 이 HTML 에서 `승인 대기 <!-- -->2<!-- -->건`
입니다. **화면에 제대로 나오는 값을 「안 나온다」고 판정하고 있었습니다.**
HTML 을 문자열로 검사할 때는 주석 구분자를 먼저 지웁니다.
